# SaaS backend operations

These procedures distinguish safe local verification from live administration. Implementation does not authorize modifying Neon or deploying production. Do not put real secrets in command history, example files, tickets or logs.

Current verification and exact external blockers are recorded in [Phase 7 readiness](phase7-readiness-report.md).
`pnpm neon:readiness --env-file <explicit-file> --output <new-report.json>` performs only provider GETs and
PostgreSQL read-only catalog checks. `node scripts/neon-e2e-plan.mjs --readiness <report.json> --output <new-plan.json>`
produces an offline plan, never live execution or authorization. Review-only configuration templates are in
`docs/config/neon-api.env.example` and `docs/config/neon-worker.env.example`; they are not loaded by Compose.
The Neon backend now rejects an unsafe branch PUBLIC CONNECT policy before creating resources, in addition
to verifying application-role privileges before activation. Do not resolve that rejection by changing unrelated ACLs without approval.

## Configuration boundaries

Existing .env files are preserved. Defaults leave TENANT_PROVISIONING_ENABLED, TENANT_ADMIN_BOOTSTRAP_ENABLED and TENANT_MIGRATION_ROLLOUT_ENABLED false. API startup does not require provisioning credentials.

| Scope                      | Required configuration when used                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| API registry               | Master runtime URL and PLATFORM_ADMIN_SECRET                                                                              |
| API tenant authentication  | JWT_ACCESS_SECRET, credential key/keyring/version and authorized endpoint allowlist                                       |
| Live provisioning intent   | Explicit enable flag, Master authorization flag, target project/branch equal their authorized IDs, finite database budget |
| Worker resource operations | Above plus NEON_API_KEY and separate NEON_PROVISIONING_DIRECT_URL                                                         |
| Admin bootstrap            | Explicit bootstrap flag plus platform authentication; operator-supplied email/password                                    |
| Migration rollout          | Explicit rollout flag, platform approval reference, persisted rollout UUID and separately authorized execution            |

Supply a random 32-byte base64url TENANT_CREDENTIAL_KEY through the approved secret manager. TENANT_CREDENTIAL_KEYS optionally holds a version-to-key JSON map for staged rotation. Keep API keys and owner/migration credentials in the worker environment only. Map runtime credentials to non-owner tenant roles. MASTER_DIRECT_URL is for explicitly authorized Master migrations; it is not a tenant migration fallback.

Production connections require verified TLS and an exact TENANT_ALLOWED_DATABASE_HOSTS list. Check branch/project identity and database/role limits against the provider plan before enabling. One project/branch can host multiple tenant databases; this is not an unlimited resource budget.

## Local verification

Use the existing shared motel development stack. From BE/:

    pnpm typecheck
    pnpm lint
    pnpm db:validate
    pnpm test
    pnpm test:master:integration
    pnpm test:saas:integration
    pnpm test:logger

The two database runners create uniquely owned temporary databases/roles on motel-postgres-1. The SaaS runner creates isolated UUID-prefixed broker objects and an authenticated loopback Neon mock. It starts independent test worker processes. It does not create another Docker project/container, use the application's existing databases as targets, or contact Neon.

Do not restart/recreate PostgreSQL during tests. A container-identity change aborts operations. If a run is forcibly killed before finally executes, retain its recorded run ID and verify database owner/comment, role marker and queue prefix before manual cleanup. Never clean by a broad database-name pattern or delete volumes.

The GitHub workflow uses a fresh isolated runner, temporary credentials and its own labelled tmpfs PostgreSQL/RabbitMQ. Its setup refuses existing motel containers and is gated to GitHub Actions. It never runs on the user's existing development infrastructure.

## Worker runtime

tenant-provisioning-worker is defined in the repository-root compose.dev.yaml under the workers profile, with a separate image target and no published port. Development scripts enable that profile on the existing motel project. compose.yaml does not define the worker and still has no PostgreSQL service.

The worker reads its separate optional BE/.env.worker configuration; no such secret file is generated by implementation. The overlay defaults the provisioning flag to false. Merely building/starting this disabled worker does not provision databases.

Health is reported in /tmp/motel-provisioning-worker-health.json with timestamp, status, healthy flag and queue depth. Docker checks freshness. A healthy disabled worker is idle, not live-ready. Queue/job failures and expired leases are alertable via health and protected GET /api/v1/admin/saas/metrics. Pool metrics describe the API instance receiving that request.

Set capacity from the actual database connection allowance: API replicas times TENANT_CLIENT_MAX times TENANT_POOL_MAX, plus Master, worker and migration connections. Defaults are 50 cached clients per API, 3 connections per tenant, 60-second idle eviction, worker concurrency 2 and at most 3 provisioning attempts. Lower these for small provider budgets. No startup enumerates/opens every tenant database.

## Provision and bootstrap after separate live authorization

1. Verify the designated Master identity, backups, migration history and permissions read-only. Review the additive SQL. Apply migrations only after explicit target authorization; implementation has not done so on Neon or the existing dev Master.
2. Verify the target Neon project/branch, endpoint allowlist and finite resource budget. Establish restrictive CONNECT/default ACL policy for existing databases in that authorized environment. The worker refuses cross-database role access and does not silently revoke privileges on unrelated databases.
3. Configure separate worker management/migration credentials, API/worker versioned credential provider and authentication/platform secrets. Enable the validated features only under the approved operational change.
4. Register the tenant, then call POST /api/v1/admin/tenants/:id/provision with the platform key. A 202 means durable intent, not successful database creation.
5. Monitor provisioning detail/history and wait for SUCCEEDED plus ACTIVE. Connectivity alone is insufficient. ACTIVE proves technical and identity schema readiness, not business data or an administrator account.
6. Under explicit bootstrap authorization, submit the intended administrator email and a strong operator-supplied password to the protected bootstrap endpoint through the approved TLS channel. Do not use a default/generated shared password or publish it in documentation. Disable bootstrap again after onboarding.
7. Verify company-specific login, tenant identity, role restrictions and revocation in the separately designated live test environment before declaring live operational readiness.

Once configured, creating another tenant does not require an API rebuild/restart. Changing deployment flags/secrets for the first time is a separate configuration operation.

## Sessions, cache and rotation

Access JWTs are short-lived bearer credentials with strict issuer/audience verification. Refresh credentials are opaque and single-use. Clients must serialize refresh requests; replay invalidates the session. Logout revokes server-side session metadata immediately. Status/role/session checks occur against the correct tenant on each authenticated request.

Tenant/company headers are not authorization inputs. Redis contains no database passwords and cannot override Master status. Metadata revision checks make suspension and mapping changes visible across instances even if Redis is stale/unavailable. If Master is unavailable, fail closed rather than routing from a stale credential or falling back to Master for tenant data.

Rotate root derivation keys by introducing a new credential version through the secret manager, retaining old versions in the keyring during the transition, configuring a separately authorized new application role/password and grants, verifying it, and updating the Master role/version mapping. Do not just replace the root key under an unchanged version and assume PostgreSQL passwords changed. Mapping/provider fingerprints cause new clients to be initialized and old clients to drain/evict. Remove old roles/keys only through an approved rotation procedure after usage verification.

JWT signing-key replacement currently invalidates existing access tokens; plan reauthentication. No automatic old-key fallback is claimed. Rotate platform keys separately from tenant roles. The API cannot grant a Tenant Admin platform rights.

## Failure and recovery

| Condition                                   | Operator interpretation/action                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Broker unavailable or confirm failed        | Pending outbox remains durable; publisher retries with delay                                  |
| Confirm succeeded but publisher crashed     | Duplicate delivery is expected and safe                                                       |
| Worker crashed before ACK                   | Broker redelivers; expired lease is claimable; final writes remain fenced                     |
| Retry handoff failed                        | Original remains unacknowledged; do not purge it                                              |
| Unknown schema/poison payload               | Inspect safe DLQ fingerprint/reason; raw payload is deliberately omitted                      |
| Neon rate limit/network read failure        | Bounded worker retries; check provider/resource budget                                        |
| Ambiguous resource creation                 | Inspect the exact reserved identity; never blindly adopt or delete an unmarked database       |
| Verified owned resource already exists      | Resume the same reserved database/role, then replay migrations/verify                         |
| Prisma migration failed                     | Preserve failure/history; inspect the reviewed SQL and actual schema on the authorized target |
| Seed or verification failed                 | Tenant stays non-active; retry only after resolving the safe failure code                     |
| Attempts exhausted                          | Failed operation remains in history; use explicit retry, not an arbitrary status PATCH        |
| Mapping corruption or unexpected privileges | Fail closed; verify identity/ACLs under separate operator authorization                       |

Reconciliation is bounded and only handles requested operations. It reuses existing pending outbox work, recovers lost published intents/expired leases and terminalizes exhausted jobs. It does not automatically delete databases, reset schema or overwrite unknown resources.

All tenant migrations are transactional SQL. A failed Prisma migration record is not automatically marked resolved. After explicit inspection of the authorized target and SQL, an operator must decide whether to repair and mark applied or roll back the failed migration history using the appropriate Prisma recovery command. Never run migrate reset/db push or pretend a failed history is successful. Test the chosen repair on a disposable copy first.

## Controlled tenant migration rollouts

Create a rollout plan through the platform-protected endpoint with an approval/ticket reference and optional tenant selection. Planning does not migrate tenants. Execute a separately authorized plan explicitly:

    pnpm tenant:migrations:run <rollout-uuid>

The command requires rollout configuration, reads eligible active mappings, applies bounded concurrency and persists per-tenant outcomes. Only one pending/running rollout may own a tenant. Re-executing a successful rollout is a no-op; expired work can resume. Failed tenants do not suppress other tenants' outcomes. Exhausted failures remain visible for operator review. No mass rollout runs during API/worker startup.

## Backup and disaster recovery

Neon provides history-based recovery and backup options; availability, configured history window and supported restore topology must be checked for the actual plan/environment. The current official [instant restore guide](https://neon.com/docs/postgres/backup-restore/branch-restore) describes root-branch recovery and its history constraints. [Backup strategies](https://neon.com/docs/postgres/backup-restore/backups) also describe logical backups. No restore, snapshot schedule or provider backup configuration was changed here.

Before rollout, record approved RPO/RTO, retention, encryption, backup ownership and recovery access. Preserve Master registry/provisioning/audit/migration history and the secret-manager keyring separately from tenant backups. Back up tenant schema/history/identity with compatible tooling. Treat a branch restore as potentially affecting all databases sharing that branch; a per-tenant logical recovery may be required to avoid rewinding other tenants.

Recovery procedure:

1. Stop or disable new provisioning/rollouts under the incident change; retain outbox and queue data. Identify the affected tenant(s), mappings, provider identities and migration versions.
2. Restore an approved copy using the provider's supported branch/history flow or a verified logical backup. Do not point live traffic at an unverified copy or overwrite healthy shared databases.
3. Verify UUID/ownership marker, technical identity, Prisma migration checksums, application-role ACLs, credentials and schema compatibility. A restored marker/metadata must correspond to the actual tenant, not just a familiar database name.
4. Restore/reconcile Master mappings from an approved registry backup/audit record; preserve deterministic identity, key version and operation history. Never reconstruct tenant ownership from an arbitrary name alone.
5. Fence/expire abandoned work, review ambiguous operations, invalidate metadata/client revisions and revoke restored sessions where required. Resume only after connectivity/authentication/isolation checks pass.
6. Record measured RPO/RTO and conduct a separately authorized disposable-environment drill. No live restore was performed in this implementation.

The Nginx example is a reviewable starting point for body limits, auth throttling and proxy headers, not a deployed gateway. Public TLS, trusted-proxy policy, alert delivery and retention remain deployment responsibilities.
